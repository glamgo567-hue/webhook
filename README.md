# webhook-service

Приём вебхуков на Flask + SQLite и очередь обработки на отдельной таблице.

## Запуск

Python 3.11+

```
python -m venv .venv
.venv\Scripts\activate          (Linux/macOS: source .venv/bin/activate)
pip install -r requirements.txt
```

API:

```
flask --app webhook_service run
```

Воркер (в другом терминале):

```
python -m webhook_service.worker --db events.db
```

Ключи воркера: `--fail-rate` вероятность сбоя в заглушке (по умолчанию 0.3), `--poll-interval`, `--once` обработать то, что готово, и выйти. Можно запускать несколько воркеров.

Проверка:

```
curl -X POST localhost:5000/webhook -H "Content-Type: application/json" -d "{\"event_id\": \"abc-123\", \"type\": \"payment_succeeded\", \"payload\": {\"order_id\": 42}}"
curl localhost:5000/stats
```

```
pytest
```

## Ответы /webhook

- 202, событие новое, сохранено и поставлено в очередь
- 200, такой event_id уже был, ничего не меняется
- 400, тело не JSON
- 422, JSON есть, но поля не те (причина в `error`)
- 413, тело больше 1 МБ

## Как сделано

Уникальность event_id держит база (UNIQUE + INSERT OR IGNORE), а не проверка в коде перед вставкой, чтобы не было гонки при параллельных запросах. Событие и задача пишутся в одной транзакции. Повтор с другим payload старое событие не перезаписывает.

Статусы задач только те, что в задании: pending, success, failed, skipped. Отдельного статуса "в обработке" нет. Когда воркер берёт задачу, она остаётся pending, но получает аренду на 30 секунд (locked_until и lock_token). Если воркер упал, аренда истекает, и задачу берёт другой воркер.

Чтобы задача не висела в pending вечно:
- попытка засчитывается в момент захвата, поэтому падение воркера тоже тратит попытку;
- после 3 неудачных попыток задача уходит в failed;
- если воркер упал на третьей попытке, задача переводится в failed при следующем проходе очереди;
- неизвестный тип события сразу skipped, повторять его нет смысла.

Результат записывается только если lock_token совпадает. Так воркер, у которого аренда уже истекла, не затрёт результат того, кто взял задачу после него.

Захват задачи идёт в транзакции BEGIN IMMEDIATE, два воркера одну задачу не возьмут. Включён WAL.

Пауза между попытками: 2 с после первой, 4 с после второй. Хранится в next_run_at.

Время в очередь передаётся параметром, поэтому в тестах паузы и истечение аренды проверяются без sleep.

## Что не сделал

- Нет таймаута на сам обработчик. Если он зависнет, зависнет и воркер. Задача не потеряется (через 30 с её возьмёт другой воркер), но процесс придётся перезапустить.
- Если воркер не запущен, задачи просто лежат в pending. Для прода я бы добавил алерт на старые pending.
- Нет эндпоинта для перезапуска failed задач.
- Число попыток, пауза и длина аренды заданы константами в taskqueue.py, не через конфиг.
